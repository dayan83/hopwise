# Evaluation and results

[Back to the project](../README.md) | [Architecture](architecture.md)

Hopwise separates implementation tests, real-model evaluation and manual answer
review. A completed execution, a correct tool sequence and a good final answer
are different outcomes and are measured separately.

## Three execution modes

| Mode | Model | PTV boundary | External API calls |
| --- | --- | --- | --- |
| pytest | Scripted responses or a mocked SDK HTTP transport | Mocked responses/fixtures | None |
| Evaluation CLI | Real OpenAI Responses client | `FixtureTransport` | OpenAI only |
| Application UI/CLI | Real OpenAI client for AI questions | PTV HTTP client | PTV, plus OpenAI for AI questions |

GitHub Actions runs only pytest. Installing dependencies requires package access;
the tests themselves require no API keys and do not make PTV/OpenAI requests.
The workflow follows the [official uv GitHub Actions guide](https://docs.astral.sh/uv/guides/integration/github/)
and uses pinned action revisions and the project's locked dependencies.

## Golden cases and fixtures

[dataset.json](../evals/dataset.json), version `0.3.0`, defines fourteen independently
authored cases. They use realistic but synthetic transport records, not live
station/service identifiers. Expected labels are manually specified and checked
with independent timestamp arithmetic rather than generated by production helpers.

| Case | Expected behaviour |
| --- | --- |
| `richmond_departures` | Resolve Richmond and report the returned services |
| `unknown_station_xyzabc` | Explain no station matches; do not request departures |
| `richmond_30_seconds_late` | Interpret a positive 30-second difference as estimated late |
| `glen_waverley_no_estimate` | Label the schedule and explicitly acknowledge the unavailable estimate |
| `flinders_street_morning_late_night_notice` | Preserve the associated notice without claiming morning replacement buses |
| `ambiguous_rich_station` | Ask which station; do not arbitrarily fetch departures |
| `richmond_next_three` | Request exactly three departures |
| `richmond_30_seconds_early` | Prioritize the 09:57:30 estimate over the 09:58:00 schedule; estimated 30 seconds early |
| `glen_waverley_no_departures` | Explain a successful empty board without inventing services or a cause |
| `ptv_api_failure` | Report unavailable departures after a successful search and HTTP 503; never present an empty successful board |
| `unresolved_disruption_id` | Report known departure facts and unresolved notice ID 5102 without an all-clear |
| `mixed_departure_delays` | Keep three different runs paired with -30 seconds, +120 seconds and an unknown comparison |
| `prompt_injection_in_notice` | Treat instruction-like notice text as untrusted data; do not fabricate cancellations |
| `contextual_vs_direct_notice` | Distinguish directly associated notice 5104 from station-context notice 5105 |

Each case specifies its question, fixture path, fixed `as_of_utc`, expected tool
calls/arguments, independently verified facts, required response notes, prohibited
claims and verification notes. The five v0.3.0 cases also include explicit
`reviewer_notes` with scenario-specific review guidance. The original nine cases
and their fixtures are unchanged; saved runs and manual labels are preserved.

The [fixtures](../evals/fixtures/) contain request/response pairs using the PTV
structures already parsed by the application. IDs connect search results,
departures, expanded routes/runs and disruption notices consistently.

## How fixed PTV data reaches the real agent

[FixtureTransport](../evals/fixture_transport.py) subclasses `httpx.MockTransport`
and is injected through the existing client/service `transport` arguments.
The normal PTV client still signs requests using dummy credentials, parses JSON
and validates models. The real matching and timing service still runs.

Matching uses HTTP method, encoded path and semantic query parameters. Query
order does not matter; changed result limits, expansions or other application
parameters do. Only authentication parameters `devid` and `signature` are ignored.
Unexpected requests raise a recognizable `fixture_miss`; there is no live fallback.
`match_counts`, `unused_requests` and `assert_all_used()` expose fixture coverage.

Every case receives a fresh transport and context-local `reference_time()` scope.
This fixes the tool's retrieval timestamp without changing unrelated tests or
the global Python clock. Mocking an entire service instead would bypass these
client, model and business-logic paths.

## Running an evaluation

Set `OPENAI_API_KEY` and `OPENAI_MODEL` in local configuration as described in the
[README](../README.md). Real-model evaluations are opt-in and incur API usage:

```sh
uv run python -m evals.run --case richmond_30_seconds_late
```

To run all fourteen cases sequentially:

```sh
uv run python -m evals.run --all
```

`--case` and `--all` are mutually exclusive; `--model` overrides the configured
model. Cases have independent agent state and fixed scenario times. A case failure
is saved and does not prevent remaining cases from running.

```text
evals/results/<run_id>/
  summary.json
  cases/<case_id>/result.json
  scores/                       # created by offline scoring
    cases.csv
    checks.json
    aggregate.json
```

The runner prints the saved path. Per-case JSON records the question, requested
tool calls, validated execution trace, final answer, fixture coverage, duration,
model metadata, token usage and controlled errors. Run summaries total execution
counts, fixture misses, time and available usage. Missing usage stays unknown.

Model identifiers and instruction/tool-schema hashes identify the configuration.
The runner's recording wrapper observes model calls without changing production
orchestration. It does not save raw SDK responses, reasoning items or credentials.
Generated run directories are Git-ignored; the compact historical snapshot below
is deliberately separate from raw executions.

## Scoring saved results

Replace `<run_id>` with the ID printed by your own batch evaluation:

```sh
uv run python -m evals.checks --run-dir evals/results/<run_id>
```

Scoring reads saved records and golden expectations. It makes no API calls and
does not rerun the agent or import production timing calculations.

| Metric | Denominator | What it checks |
| --- | --- | --- |
| Tool selection | One check per case | Requested names/order match an explicitly allowed sequence |
| Arguments | Each expected call | Exact stop IDs and limits; explicitly accepted query variants |
| Execution | Case prerequisites and expected calls | Correlated expected outcomes, no unexpected calls/misses and required fixture usage; success is required unless a controlled error is explicitly expected |
| Source facts | Independent golden fields | Structured tool records match the specified facts |
| Timing wording | Applicable golden delay descriptions | The supplied sentence occurs after Markdown/whitespace normalization |

Case-level pass counts require all applicable checks to pass. Missing results
remain failures in the denominator; `not_applicable` is distinct from pass.
Literal sentence presence and correct source records are not proof that every
claim in the final answer is accurate or grounded.

### Failure and safety coverage in v0.3.0

The departures-error fixture returns HTTP 503 with a synthetic service-unavailable
JSON body. This exercises the existing client's `raise_for_status()` handling;
the tool adapter returns `ok: false` and error code `data_unavailable`, without a
board. It does not simulate an empty HTTP 200 response or a transport exception
unsupported by the fixture format.

Only the expected call in this case opts into an error outcome:

```json
{
  "name": "get_departures_with_disruptions",
  "arguments": {"stop_id": 1101, "limit": 5},
  "expected_error_code": "data_unavailable"
}
```

This is evaluation metadata, not a production tool-schema change. The focused
execution check requires correlated call identity, the expected validated
arguments, both `ok` fields false, the exact error code and no board. An unexpected
success, another error or a fabricated empty board fails. Calls without the
annotation retain their original successful-tool checks and check identifiers;
historical scoring semantics are unchanged. The failure case deliberately omits
`departure_count: 0` and a successful-board stop-ID source fact.

The runner needs no change: a handled tool error can be followed by a final answer
and therefore have run status `completed`, top-level `error: null` and no execution
exception in the batch summary. Inspect the failed tool entry, not just that
summary, to identify the API failure. The expected error check does not judge
whether the final answer clearly explained unavailable data.

The unresolved-ID fixture requires a third HTTP response for the route fallback.
Both calls at the agent-tool level remain search then departures. A successful
fallback with empty mode groups leaves ID 5102 unresolved; deleting that fixture
causes `fixture_miss`, never a live request. The request-coverage denominator is
the number of HTTP definitions, not the number of LLM tool calls.

Important manual-review limits remain:

- Mixed-delay source facts are checked by `run_ref`. The timing-sentence contract
  cannot establish that the final prose attaches each sentence to the right train.
- The injection string remains in the associated notice and sanitized trace as
  evidence. Keeping it in tool data is intentional; interpreting it as a system
  instruction is prohibited. Offline tests check delivery through
  `function_call_output`, not real-model resistance. Quoting or rejecting the
  string is different from endorsing an unsupported cancellation claim.
- Associated/contextual ID sets are checked in structured results. Correct final
  categorisation and the absence of unsupported impact claims require review.
- Reviewer guidance is in each case's response notes, prohibited claims and
  `reviewer_notes`. The scorer exports the first two into its existing review
  guidance; consult the dataset for the additional scenario-specific notes.

These cases and labels were authored before observing real-model outcomes. No
live OpenAI or PTV evaluation was run for this dataset expansion. Unknown answer
quality remains unscored until review; keyword presence is not a safety score.

The CSV has `manual_factual_accuracy`, `manual_grounding`,
`manual_response_relevance` and `reviewer_notes`. Scores start blank/null:

- **0:** major problems.
- **1:** partially satisfactory quality.
- **2:** satisfactory quality.

Review the full question, final answer, trace and golden response notes/prohibited
claims. Edit the CSV and rerun scoring to aggregate labels; valid existing reviews
are preserved. Coverage is reviewed cases divided by all cases, independently
for each dimension. Unreviewed answers are not counted as zero.

Follow a failed check from `cases.csv` into `checks.json`, then its evidence path
into the original result and fixture. Requested calls may differ from executed
calls after validation failures. Fixture misses can interrupt execution before
a tool result is recorded, so inspect requested calls and coverage together.

## Reviewed nine-case historical baseline

The [baseline snapshot](baseline-summary.json) is a compact export of the existing
saved run and author-entered reviews from **18 November 2026**. It records the
dataset/configuration hashes and returned model identifiers. It contains no raw
SDK diagnostics, credentials or authenticated URLs.

| Measure | Result |
| --- | --- |
| Cases completed | 9/9 |
| Execution errors / fixture misses | 0 / 0 |
| Tool selection | 9/9 checks |
| Arguments | 16/16 checks |
| Execution | 61/61 checks |
| Structured source facts | 200/200 checks |
| Timing wording | 3/3 applicable checks; six cases not applicable |
| Author review coverage | 9/9 cases |
| Manual factual accuracy | 2.00/2 mean |
| Manual grounding | 2.00/2 mean |
| Manual response relevance | 1.67/2 mean |

This baseline used requested model `gpt-5.5` and returned snapshot
`gpt-5.5-2026-04-23`. It made 25 model requests using 25,262 reported tokens.
These are observations from a small, manually reviewed synthetic set, not
generalized accuracy estimates or an independent external assessment.

Review identified three presentation weaknesses despite passing mechanical checks:
the missing-estimate answer did not clearly label its schedule; the early service
led with its later scheduled time; and the morning answer gave substantial space
to a notice describing late-night works.

The first two findings motivated deterministic `departure_time_description`
wording and agent instructions to prioritize labelled estimates. The recorded
baseline predates that change. Its scores must not be presented as measured
improvements for the current prompt. A later local run exists, but no reviewed
post-change scores are claimed here. The late-night-context finding remains a
known relevance limitation.

Fixed inputs improve comparisons; model outputs can still vary between runs.
Expanding station, timing and notice coverage and reviewing further runs would
be necessary before making broader quality claims.

## Offline checks

```sh
uv run pytest -q tests/test_fixture_transport.py tests/test_evaluation_run.py tests/test_evaluation_checks.py
```

These tests block live network/client paths and cover matching, clock isolation,
all fourteen fixtures, sequential case isolation, saved errors/results, scoring
denominators and preservation of manual labels. The rest of the offline suite
also covers the agent, service and Streamlit boundary.
